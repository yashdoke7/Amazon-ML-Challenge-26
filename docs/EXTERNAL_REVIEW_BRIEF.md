# External review brief — Amazon ML Challenge 2026

_27 September 2026, ~16:55 IST. Deadline 23:59 IST today. This is a factual handoff for an independent method review; detailed evidence is in [FINDINGS.md](FINDINGS.md), [NEXT.md](NEXT.md), and [RULES.md](RULES.md)._

## Task and constraints

For each deduplicated Source 1 business, output **all** matching Source 2 and Source 3 IDs, or an empty list. Fields are business name, address, country, and record ID. The metric is **macro F0.5 per Source 1**; false positives are expensive, and a true singleton needs an empty prediction. Train has US and India; test has **663,106 US, 809,986 India, 259,452 France** queries, so France is unlabeled in train. There are 1,732,544 test queries and about 10.3 million target records. The final ZIP needs the match TSV, every query's last-stage candidate IDs, runnable code, and methodology, under **512,000,000 bytes**. No external business lookup, remote inference on supplied records, or external data augmentation. Locally used pretrained model weights must satisfy the stated MIT/Apache 2.0 and parameter rules. Hardware: i9-14900HX, 32 GB RAM, RTX 4070 laptop 8 GB VRAM; AWS credits exist but have not produced a measured advantage.

## Current submitted method

1. Normalize names and addresses with Unicode/accent folding and `anyascii` transliteration while retaining original-script evidence. Build local DuckDB/inverted lexical indexes on the supplied targets. Broad candidate routes use rare name/address tokens, normalized keys, domain stems, address overlaps, and fuzzy name ranking. An exact local word unigram/bigram address TF-IDF search rescues India candidates; later routes add local character 3–4-gram TF-IDF address top 10 for US and name top 5 for India. These searches are over the entire relevant target index, with no external text.
2. A learned 23-feature blocker retains top 40 lexical candidates per query, combined with the extra retrieval candidates, keeping the final candidate TSV small enough for the ZIP. A 35-feature LightGBM matcher with string, address, numeric, source, transliteration and comparison signals scores the pairs. A separately trained specialist handles missing-address/frequency cases. Training uses hard negatives, including deceptively similar names and addresses. Country thresholds are selected on labeled development data; France uses the general setting.
3. Apply a top-11 match cap based on the largest labeled true group, then resolve target IDs predicted for multiple Source 1 owners by score. Validate one row per query, legal target IDs, matches as a subset of recorded last-stage candidates, and archive CRC/hashes.

The best **confirmed public score is 0.9317**. The exact verified package is backed up in `output/final_public_0p9317_verified/`; its ZIP is **497,281,183 bytes**. Earlier public scores were **0.876**, **0.926444**, **0.92817**, and **0.928661** as candidate routes and matcher improved. Local macro F0.5 for the latest route is **0.939906 on all 22,133 development queries** and **0.933266 on a separately held-out 1,994-query frozen validation split**. These are not private leaderboard estimates. The visible top teams are around 0.988–0.991 public; their methods are unknown.

## What we tested and learned

- **Better matcher and multilingual features:** A 20k-query 27-feature numeric LightGBM improved full development 0.88331→0.89574 against its comparable baseline. Adding transliteration-based features improved 0.897608→0.908314 on full development and 0.892716→0.904159 on frozen validation in the earlier model comparison; India benefited most. A later ~190k-query hard-negative matcher and blank-address specialist reached 0.918651 on the comparable full-development candidate route. These are different candidate pools and should not be compared as an isolated model gain.
- **Candidate compression:** Naive top-20 name/address truncation dropped 13–14% of reachable true links. The learned top-40 blocker retained 70,735/70,741 broad-reachable true links on 22,133 development queries while reducing candidates from 4.74 million to 864,450. Top-45 added 106,709 pairs without changing match output. Thus widening this existing pruning stage is unlikely to create a major gain.
- **India word-address TF-IDF:** Full local index search, top-20 target IDs per India query, improved comparable full development **0.923221→0.931832** and frozen validation **0.918447→0.927518**. This generated the 0.926444 public package. It directly recovered cross-script/weak-name cases but did not solve all of India.
- **US word-address and name retrieval:** Measured gated routes raised full development to **0.936843**, frozen validation **0.931181**, and public score to **0.928661**. A separate US exact address probe added 31 true links and zero false links on frozen validation, but broad rollout had runtime and ZIP costs.
- **Character TF-IDF retrieval:** US character-address top 10 plus India character-name top 5 raised full development **0.936843→0.939906**, frozen validation **0.931181→0.933266**, and public **0.928661→0.9317**. Exact US char-address top 5 found 1,046/2,438 previously absent US true links in a development retrieval audit. India character-address top 5 found only 38 additional true links over the current India word-address route and was rejected. A broader India character-address/name fusion found 249 novel true links at a 20-ID quota, raising India candidate-only oracle only to 0.980472.
- **Embeddings:** Multilingual MiniLM on the RTX 4070 encoded 1,024 names in 0.165 s versus 2.172 s CPU, but embedding cosine as pair features gave only about **+0.0004** over a comparable larger lexical model on the tested validation sample. Full-index Indian-script name ANN top 100 recovered **121/1,611** retrieval misses; exact transliterated character TF-IDF recovered **102/1,611**. These results do not support a hurried 50 GB vector build or a full embedding replacement. Most inference time is CPU index retrieval and Unicode/string features; LightGBM scoring was <5% in a 1,000-query profile.
- **Grouping:** An earlier learned predicted-sibling context reranker improved 0.918764→0.919563 development and 0.910586→0.910885 validation on an older candidate pool, too small to promote. A new rule comparing rejected candidates with selected target anchors across 50 name/address/number thresholds **hurt** full development **0.939906→0.938746** and frozen validation **0.933266→0.932028**. It added too many false links despite strong similarity.

## Actual bottlenecks and oracle caveat

In the previous top-40 plus India-address development candidate union, **4,391 true links were absent** from candidates and **5,708 true links were present but rejected**. The expanded current candidate-only oracle is **0.987535** on development: this assumes ground-truth labels select perfectly from every retrieved candidate. It is **not an achieved model score or forecast**; the current actual development score is 0.939906. US candidate-only oracle is 0.993348, India 0.978769; India remains the larger retrieval weakness. Even perfect pair decisions on the current pool would not reach 0.99 on that labeled mix.

An even more optimistic **0.996882** development/**0.995486** frozen-validation *group-propagation oracle* assumes perfect S2/S3 target-to-target entity clustering and perfect group selection. Only 69/22,133 development groups lacked any true target candidate; many partly retrieved groups could, in principle, be completed from a correct anchor. We have **not** built a reliable clustering method: similar names and addresses also describe distinct businesses, and the simple anchor rule failed. The top teams' ~0.99 methods are unverified; avoid inferring them solely from their score.
